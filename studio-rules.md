## Product thinking (every agent, every engine)
Before anything is built, think like a product team and write it down in the feature's docs: the user problem and who has it; the user journeys; edge cases; security and privacy; resilience and UX (slow or failed network, repeated taps, closing the app midway, empty/loading/error states); and acceptance criteria. Explain the intended user outcome, trade-offs and how success will be measured. Work out the scenarios yourself from the product and the founder's words. Never ask for, search for or use an outside "reference checklist" of scenarios: it would hide what you failed to think of. Group the founder’s checklist under Core user journeys, Edge cases, Security and privacy, and Resilience and UX. Show verified passes against the known total. The founder approves the contract; tests are written by someone other than the builder; review is independent. A scenario counts as passed only with real test evidence.

## Every reply to the founder (Claude, Codex, other models, any tool)
Size the reply first. A simple question or small edit gets a few lines and no dashboard. A meaningful result gets: one outcome heading with an icon (✅ done, ⚠️ blocked or risk, ❌ failed, 🔍 findings, 🛠️ in progress); one italic line on what happened and what did not (end with your role tag, e.g. [Quinn — QA]); the evidence as a compact table; at most about 120 more words; one next action with its owner. Aim for 30 seconds of reading. Add a short Technical Appendix (what, why, where, PM mental model, example) only for a genuinely new concept.

After meaningful project work, end with the founder dashboard. Use these fields in this order, as a card if the tool can draw one, otherwise a Markdown table:
**<Product> — Founder dashboard** · Feature progress (% and passed/total acceptance criteria; "Not measurable" if none approved) · Tests passed (passed/run, naming failed and skipped) · Founder decisions (count) · Critical open defects (count) · Decision needed (one question, options with one Recommended, plus your recommendation) · Session recommendation (Continue, Compact, Switch or Escalate) · Recommended model (Fast, Balanced or High reasoning) · Handover status (Saved, Synced, Verified or Not saved).
For a pilot or feature update, use the progress report instead: current stage; milestones x/y with a bar; acceptance scenarios passed/total; critical defects; founder interventions; additional spend; what was achieved; what remains; resource status; founder action.
Unknown shows "Unknown", never 0 or a guess. Colour words: Passed green, Partial orange, Blocked red, Pending grey.

## Agent consumption
When asked about cost or usage, or in any milestone report, show consumption by agent role and model: tokens in and out, model identity and its source, available cache and reasoning counts, and reported cost, using only measured numbers. The Studio records them (Agents tab → Agent consumption, or GET /api/products/<id>/usage). Say "Unknown" where an engine did not report a figure, and never invent token, context or subscription numbers.
